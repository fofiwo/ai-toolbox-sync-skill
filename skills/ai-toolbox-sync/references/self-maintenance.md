# 管理器维护、升级与旧收藏迁移

## 先确定同步对象

先执行 [首页分流](../SKILL.md#同步前先分流)。本流程内还要区分“从公开库更新本机”与“把本地通用修改发布到公开库”；只明确更新本机时不推送。读取公开源码不依赖私人库邀请、绑定或写权限。

ai-toolbox-sync 自身源码的唯一维护来源是 https://github.com/fofiwo/ai-toolbox-sync-skill 。准备修改、已有修改要续接、跨电脑更新或同步本管理器时，进入独立公开源码 checkout，先读该库 AGENTS.md、PUBLICATION.md，运行 release.py inspect，说明安装版、源码工作区和远端差异。已明确授权同一改动则继续；未知本地修改或分叉先解释并等待选择。发布只用 release.py 的门禁，不用私人库的 collect/push，也不把已安装目录整包复制到公开库。

普通工具同步继续使用用户明确绑定的私人库，直接使用原生 Git 和本项目脚本。管理器不加入 toolbox.json、taskSync.resourceIds、resources 或本项目私人资源分发目标；第三方安装身份记在库外 installation.json，不改成自建以便收藏。源码发布、本机升级和其他工具的收藏同步分别验收。

## 随包来源与每机安装记录

`SKILL.md` 的 `metadata.repository` 与首页保存本管理器当前公开来源；完整源码树的 Skill 子目录为 `skills/ai-toolbox-sync`，版本文件为该目录内 `VERSION`，仓库根的 README.md、INSTALL.md、PUBLICATION.md 与 release.py 提供安装和发布入口。只装了 Skill 子目录时，AI 根据随包来源在独立目录取得并审阅固定公开源码，再使用根目录工具；不假定安装目录内有 release.py，不为找到工具先建立私人绑定。来源定位只需随包记录和已知安装收据，不搜索其他聊天或私人收藏。来源与可信收据不符按下面的旧机流程处理。

每机默认收据为用户目录下 `.agents/ai-toolbox-sync/installation.json`；已有显式收据路径时复用，不迁移或覆盖其他实例。由 AI 在安装、更新和发布验证后按现有结构增量写入：

| 记录 | 内容与验证要求 |
|---|---|
| `source` / `sourcePath` | 当前公开来源与 `skills/ai-toolbox-sync`；历史 UPSTREAM 及私人 remote 不作更新源 |
| `version` / `sourceStatus` | 实际磁盘 VERSION；已核实公开内容为 published，含未发布通用改动为 local-unpublished |
| `commit` / `tag` | 只有安装内容符合固定公开提交时记录实际提交；标签须核实存在且指向同一提交，不存在则 null，不猜造 |
| `baseCommit` / `installedFilesSHA256` | 本地开发或定制的可信起点与逐文件实际摘要；未知起点明确未知，不能把现状当作原版 |
| `localCustomization` | 存在定制时另记基线、摘要与用户本次差异处理选择；保留现有授权、历史与其他字段 |
| `host` / 验证时间 | 磁盘一致、宿主发现及新会话实际加载分开记录，未执行的保留未验证 |

写前比较旧记录摘要，修改时保留可恢复的旧记录；并发变化停止并重新比较。收据留在库外，既不随公开包分发也不从其他电脑复制；缺少收据只影响旧改动归因，不影响从已知公开来源只读检查。创建收据和安装升级分别验收，不能用补写记录冒充更新成功。

## 管理器版本

Skill 内的 `VERSION` 是唯一版本来源；元数据、README 当前版本和页面页脚由公开库 `release.py bump` 一次更新并重建摘要。修复用 patch，兼容功能用 minor，不兼容变更用 major；草稿序号用 prerelease，验证稳定后用 final。开发提交不逐次升版；用户请求同步且有新发布内容时，AI 依据变化选级别，已有高于远端且匹配本轮内容的待发布版本直接复用，不重复升版。没有变化不制造版本。

发布入口拒绝变更代码复用远端版本、版本倒退或覆盖已有标签；main 和唯一的轻量 `v<VERSION>` 标签在一次原子推送中发布并核验。原子推送不受支持时停止，不拆成部分发布。网络结果不确定时先核实远端分支与标签，保留本地标签；不能为重试移动旧标签。历史未带 VERSION 的提交仍可审计，新的发布头必须具备版本文件且各处一致。

本机开发安装记录实际 VERSION、基线提交与 local-unpublished；发布成功后再核对远端标签、归档和安装文件摘要，才把安装收据改为相同的 version/commit/tag。磁盘版本、已加载会话与宿主实际可用分别报告，不因发布成功改写收藏、绑定或其他工具的版本。命令完整流程见公开库 PUBLICATION.md。

## 其他电脑更新、开发与续接

### 旧电脑缺少来源或仍加载旧指令

先只读核对宿主实际发现的 Skill 路径、`SKILL.md` 元数据、`VERSION`、库外安装收据和可信源码 checkout 的 remote。路径、版本和摘要未核实前，不凭另一台电脑已经发布就声称本机已升级。若存在多份同名 Skill，指出实际使用的副本，保留其他副本与修改；安装目录更新后，已打开会话仍可能持有旧指令。

本管理器的当前公开来源已在首页记录。旧文件中的“尚无公开发布 URL”、私人收藏 remote 和 `UPSTREAM.json` 的历史第三方 repository 均不能覆盖该来源；已知来源时由 AI 自行读取 README.md、INSTALL.md 和固定提交，不再要求用户重复提供链接。可信安装收据指向其他项目或定制分支时，先说明冲突并让用户选择，不能静默改绑。

旧安装没有可信收据或 VERSION 时，先保留实际文件摘要，在独立目录取得并审阅固定公开源码，尽可能寻找旧包或可信历史，逐项展示本机与新版差异；无法归因的内容标为未知并让用户选择保留或合并，不把当前文件直接登记成原版基线。保留私人清单、绑定、未提交修改与库外状态；没有旧版维护命令时使用独立审阅的新工具，不能为升级先覆盖旧安装。完成后记录当前公开来源、版本、提交与逐文件摘要；磁盘更新和新会话实际加载分别验证。

AI 执行检查与获准的操作，用户只处理真实冲突的取舍、敏感登录或必须本人完成的确认。维护、保存本地进度、公开发布、安装更新分别验收；仅使用 Skill 不联网，不安装后台监听或全局 hook。

### 修改前与续接

1. 明确公开源码 checkout、工作分支、宿主安装目录和库外安装收据。运行 `release.py inspect`，用版本号、Git 共同祖先和实际文件摘要说明双方变化；较高版本号不能代替提交包含关系。
2. 为维护源码和安装版，运行 `release.py start --installed <Skill目录> --receipt <库外installation.json> --paths <本轮精确路径...>`。只改公开源码时显式用 `--source-only`，报告安装未检查。`--paths` 是提交范围，省略时只限制公开文件白名单，不提供任务范围隔离。安装收据需有固定公开来源和逐文件基线；缺失时先查可信旧安装包，不把现有文件直接认定为原版。
3. 干净源码且仅远端领先时，在本次更新授权内说明变化后用 `start --align` 安全快进；安装目录另按下文逐文件更新，完成后以 `--restart` 记录新基线。源码检查、安装文件符合旧收据、安装是否与新源码一致是三个状态；`installationVerified` 不代表新版已安装。
4. 已有源码修改、未推送提交或安装定制时先保留。AI 比较“基线→本地”和“基线→远端”，简述双方功能变化和建议，由用户选择保留、合并、采用远端或暂缓。获准继续源码用 `--accept-local`，获准保留安装定制另用 `--accept-installed`；这两个参数不能跳过分叉和远端领先检查，也不会复制安装目录到公开库。
5. 开始基线保存在当前 worktree 的 Git 私有目录，包含分支、开始提交、当时远端、源码摘要、提交范围和安装/收据摘要。同条件续接保留原基线；分支、历史、远端或安装变化须重新比较，获准后 `--restart`，旧记录归档保留。记录不进入公开库或私人收藏。

### 保存进度与正式发布

- 本地保存：AI 审阅并测试后，更新 manifest，只暂存本轮获准的精确路径，再运行 `release.py finish`。它验证实际 index 的完整清单与摘要，拒绝范围外暂存、冲突或同一文件暂存后又被修改；未暂存文件不属于本次提交。它核对开始基线及安装状态，并刷新远端状态。断网、远端领先/分叉或版本尚未提升时，仍可保存本地提交，但明确标记不能据此发布；不要为保存进度强制升版。
- 在开始检查前已改动、断网或合并需要先保存时，运行离线的 `release.py stage-check` 核对实际 index；明确报告只有本地保存检查，未建立完整维护基线、未核实安装或最新远端。它也不自动暂存、提交或上传。
- 获准本地提交后，AI 使用原生 Git 提交，再运行 `release.py verify-commit`，核对实际提交的 tree、父提交和分支与检查收据完全一致。内容或 hook 发生变化则保留现场，不发布；后补无效提交不能消除历史门禁。下一次修改重新准备并核验，不能复用旧收据。用户只要求修改时仍遵循宿主的提交授权规则。
- 正式发布：用户请求本次同步/发布后，再实时检查远端。双方有变化先保护本地进度、审查合并并重新测试；准备或复用高于已发布版本的版本号，重建摘要，审阅暂存、提交并核对，最后执行 `release.py check` 与 `release.py push`。发布只允许 main，开发和本地保存允许独立分支。版本与标签门禁、原子推送、发布后的远端复核继续生效；不自动改写历史或强推。

`finish` 不执行测试，也不代表已经提交、已经发布或安装已更新。收据与前台命令提供合作式检查，外部手工编辑或直接 Git 命令可以绕过；不能承诺全局强制触发。只在既有授权内提交，不因一次保存自动上传。

### 新版本增加文件时

旧白名单挡住新路径时，AI 先运行 `release.py review-update <固定远端SHA>` 获取新增路径和需审查的提交，再逐项审阅新增文件、release.py 的策略变化及相关历史；未知路径先按名字判断是否可能涉及凭证，不能直接读取敏感文件。确认属于干净公开源码后，运行 `release.py approve-update <同一SHA> <全部精确新增路径...>`，随后再 `start --align`。批准只绑定当前起点到该 SHA 的精确文件集合，不能使用目录或通配符，远端变化后失效；不会执行远端发布脚本或自动安装。

若新版改变了旧校验器不支持的数据格式，或旧安装尚无上述入口，先在独立目录取得固定公开源码，由 AI 审阅校验器与迁移差异后再使用新工具验证；不得关闭旧门禁、执行未审阅代码或把“取到源码”当作升级成功。源码固定后，安装与收藏兼容仍按下文验证。

## 数据位置与升级兼容

| 内容 | 位置与升级处理 |
|---|---|
| 管理器通用源码、空 catalog/data.js、空 discovery-data.js | 公开库及固定提交安装包；只审核这些文件 |
| toolbox.json、用户已收藏工具源码、稳定 id/sourceIdentity/parentId | 原私人库；管理器升级不写入、不重编号、不改 remote |
| decisions、version-checks、binding、binding-pointer、journal、备份、安装收据 | 本机库外原位置；不从安装包初始化或迁入共享库 |
| 收藏展示、盘点快照和工作台 | 本机库外；从原清单/记录按需重建到新目录，旧快照保留 |

schemaVersion=1 继续读取旧 management 字段和新的 state 五轴。只按已核实的稳定身份叠加本机状态；同 id 的 kind/sourceIdentity/parentId 冲突报错并保留现场。新工作台复用原清单、可选记录与绑定，不靠名称去重，不扫描或自动收藏工具。没有本机记录时状态未知，不据此取消收藏。

### AI 执行升级

1. 固定公开提交、核对 SHA256SUMS.json，在新目录审阅；读取库外安装收据确定旧基线。逐文件比较旧基线、实际安装和新源码。无可信基线则说明不能判定改动归属；有本地定制时先解释损失范围和建议，等用户选择，保留未选改动。
2. 仅处理管理器时不连接私人远端、不要求私人库认证，也不为升级遍历绑定或读取收藏内容。只有已知安装目录内含真实 catalog/discovery 数据、或已知事务可能写入本次替换文件时，才在授权内检查相关本机定位信息、必要输入摘要与锁，保留原位置；缺少相关授权先交接，不扩大扫描。升级不重置记录、不移动库根、不复制机器路径或凭证。存在进行中的写入事务时先核对负责方，延后涉及的替换。
3. 旧版曾在安装目录生成真实 catalog/data.js 或 discovery-data.js 时，先备份并迁到库外。若找到原 toolbox.json，优先从它重建；找不到时保留旧展示快照并报告缺少权威清单，不能从空模板推断应清空收藏。数据迁移结果核实后才替换这些模板。
4. 对本机升级只逐文件应用已批准的新/改源码，再次核对旧文件摘要。仅存在于本机且即将被替换的修改先保存库外副本；已有可信 Git 历史可恢复的内容记录提交即可，不必每次复制整个安装。删除须列明并获得范围授权。区分磁盘文件、运行中的管理器脚本和会话已加载指令：先从独立审阅目录执行维护，确认没有涉及这些文件的运行进程/未完成事务后应用；仅已加载文本不等于脚本仍运行，不得因此无限延期。无法确定运行状态或存在写者时延后相关文件，记录具体阻塞与重入条件；不结束用户进程、不擅自安装后台续办。中途失败保留恢复材料和待办，不把部分替换当成功。
5. 本次确需迁移真实展示数据或重建工作台且已获相应本机读取授权时，用原非空清单、记录与绑定生成新的库外工作台，核对资源 id/数量、身份、收藏状态及实际安装状态，并确认输入字节摘要不变。仅替换通用指引且不涉及展示数据时跳过，不为验收额外读取收藏。身份冲突或 schema 不支持时停下，不降级或重建空状态。执行适用的合成兼容测试，另行报告真实宿主发现与调用证据。
6. 成功后只更新库外安装来源/提交/文件摘要；原 binding-pointer 继续指向原绑定，原收藏、授权范围和未完成任务保持原状。源码发布成功不表示本机已更新，新文件就位也不表示已打开会话重载。

用户要求修改并同步本机管理器时，在同一授权范围内检查并完成源码发布与本机应用；只有对应步骤都核实才称整体完成。仅有发布授权不能覆盖未经选择的本地定制。用户要求本地修改但未要求本次发布时，可应用已审阅的开发工作区，记录基线提交、实际文件摘要与 local-unpublished，不能把基线提交冒充新版远端。待办文件本身不会自动执行；续接时先核实旧待办与实际磁盘状态，不能承诺换会话自动完成。当前会话的新版指令接收与新会话发现仍单列验收。

0.3.0-draft 起依赖为 Python 与原生 Git；旧绑定中的 cli、XDG 和旧管理器配置字段保持历史原样但不再调用。原 Git 根、远端、资源 id、收藏、基线、journal 和 workItems 保留；不重建仓库或改写历史来解除依赖。

## 私人库曾收藏管理器

先只读列出管理器的精确稳定 id、contentPath、对应绑定和引用。以来源、路径和实际内容确认身份，不能仅凭名称删除。先将需要保留的通用功能逐项审查并发布到公开库；没有公开写权限或发布未核验时，保留私人源码。

取得本次明确移除授权后，按原清单摘要做冲突检查，只移除已核实的管理器条目和独占源码路径；清单中其他条目、分类、排序及未知字段原样保留。若其他条目引用该路径或目录含未审查文件，暂停删除并解释。核对 README、测试和配置引用，修复直接失效引用。正常提交保留可恢复历史，不改写私人 Git 历史，不换 remote。

库外只解除该管理器对应的 resourceIds/resources 绑定和失效展示项；其他资源绑定、decisions、journal/pending、pointer 不清空，有进行中的管理器事务先保留并解释。旧决定记录作为历史保留，不将“源码已发布”写成“其他工具已同步”。没有绑定时不伪造一个以通过检查。

最后分别报告：公开源码提交与远端核验、私人管理器条目/源码移除、本机是否已应用升级、原收藏兼容检查、实际宿主可用及未验证项。权限或网络失败只标对应步骤 pending，不宣称同步成功。
