# 私人仓库接入与新电脑引导

先检查，再下载。本文是按授权执行的引导，不是自动安装器；不自动改 PATH、升级旧安装或覆盖同名目录。

## 0. 私有库接入：先明确身份，再处理当前阻塞

用户尚无仓库或要求从零配置时，先执行 [首次配置](first-use.md)；不要把提供仓库地址作为开始检查的前提。已有仓库才进入下面的对接流程。

用户提出“对接这台电脑”后，先复用会话已给出的仓库、账号关系、目标宿主和操作范围，不重复询问。首次交接前用一句话或小表展示：目标仓库 OWNER/REPO、仓库所有者、用户确认的接收账号、浏览器实际账号、CLI 实际账号、仅恢复或需要上传。区分用户选择和已验证事实；未知项写“未核实”，浏览器登录不等于 CLI 登录，当前登录账号不自动成为接收账号。组织仓库的 OWNER 是组织，不把它当作可登录个人账号；邀请由该库有管理权限的人操作。

缺少信息时只问会改变下一步的必要项，例如接收账号或操作范围。可独立完成的本机检查继续执行。不要硬编码本次开发者账号或仓库。

| 方式 | 适用情况 | 用户必须配合的部分 | AI 负责 |
|---|---|---|---|
| 同一个 GitHub 账号 | 本人的第二台电脑，使用仓库所有者或已获权限的账号 | 必要账号选择、密码/验证码/双因素认证，以及宿主强制本人操作 | 检查并复用有效认证，执行已授权的普通页面操作，恢复资源并建立本机绑定；不需要协作者邀请 |
| 不同 GitHub 账号 | 另一人或另一账号使用同一私有库 | 有权者确认邀请对象与权限；处理敏感输入、宿主强制本人操作或用户保留的步骤 | 在明确授权内完成可执行的邀请/接受/认证步骤；未获发出邀请授权时给主人具体指引；接受目标邀请后验证真实访问权限 |

不同账号未获权限时，知道仓库链接或已安装 Skill 都不能访问。协作者会获得相应仓库内容的访问权，不是仅分享一个 Skill；个人账号仓库的协作者通常具有写权限，不承诺可以授予只读权限。以实际仓库类型和 GitHub 当前权限选项为准；若只愿分享部分内容，提供获准的 Skill 包或使用对方自己的库，不擅自扩大权限。

**AI 执行优先。** 用户已明确要求将接收账号接入目标库时，在该授权范围内由 AI 检查并接受匹配的访问邀请；“邀请已发出”触发重新检查和实际接受，不是让用户再去找链接并点击。先核对接收账号、仓库、邀请者及页面显示的权限；目标不符、额外组织成员身份或新条款等超出范围时才询问。发出邀请会向他人新增访问权，仍须单独覆盖具体对象与权限；接受邀请不授权上传。用户明确保留本人接受/批准的决定时尊重该选择，后续明确改为 AI 执行时复用新授权。

### 按状态推进，不把认证和邀请当成同一个问题

先核实可观察的实际身份和访问状态，再走下表；这是有分支的流程，不要求所有人依次登录、邀请和授权。已可访问的不同账号也跳过邀请。

| 已知状态 | 当前动作与完成标准 |
|---|---|
| 接收账号未确定，或实际身份与选择不符 | 说明具体不符项，只询问使用哪个账号；确认前不切换账号、不向猜测的账号发邀请 |
| 已确定需要邀请，尚未发出 | 进入下文“仓库主人发邀请”；先解决仓库访问授权，不反复启动 CLI 设备授权 |
| 邀请已发出、尚待接受 | AI 进入下文“接收者接受邀请”，核对并接受已授权目标邀请，再实查访问；邀请已发送不代表访问已生效 |
| 权限未知，例如只看到 404 | 核实账号、地址和邀请状态；404 不能单独证明仓库不存在或没有邀请。确需 CLI 查询而 CLI 未认证时才先完成 CLI 授权 |
| 目标账号具有浏览器访问权限，CLI 未认证 | AI 完成该接收账号的 CLI 官方授权中已获准且工具可执行的页面操作，仅交接必要敏感输入或宿主强制确认 |
| CLI 账号正确、仓库 API 可读 | 验证实际 Git 读取；Git 失败时区分网络、权限、helper 路径，不重新发送邀请或盲目要求登录 |
| CLI 和 Git 读取均已验证 | 只读取得收藏清单，让用户选择，再比较并恢复 |

### 不同账号：邀请交接必须包含入口

以下 OWNER/REPO 和 RECIPIENT 是说明占位符；面向用户时替换成已确认值并输出可点击链接，不让用户自行拼接地址。只交接当前阻塞步骤，后续步骤可简述，不一次要求完成全部流程。

**仓库主人发邀请。** 指明由哪个账号或哪位有管理权限的人操作，在指定浏览器登录该账号，打开 `https://github.com/OWNER/REPO/settings/access`；导航路径为目标仓库 → Settings → Collaborators（组织仓库可能显示 Collaborators and teams）→ Add people / Add collaborator，搜索准确用户名 RECIPIENT，核对后按当前页面选项发送邀请。账号与权限方案由有权者确认；一般接入请求不授权 AI 新增协作者。AI 可在明确授权和宿主允许范围内准备或执行步骤；用户保留发出邀请时，只准备页面并交接。若页面或按钮不同，检查实际页面后给出正确路径，不凭模板声称已打开或已发送。

**接收者接受邀请。** AI 先核实指定浏览器右上角账号菜单显示 RECIPIENT，打开 `https://github.com/OWNER/REPO/invitations`，核对目标后点击 **Accept invitation / 接受邀请**。页面若直接跳转至已可访问的目标仓库，验证现有访问并跳过接受，不重复邀请。也可从已授权可见的 GitHub 邀请通知进入；邀请邮件或主人复制的官方邀请链接只作为必要时的后备入口，不为找链接擅自访问邮箱、不要求将含邀请标识的完整链接发到聊天。只有工具无法执行、宿主强制本人确认、权限超出范围或用户明确保留手动接受时才交接，并提供下文完整提示。

邀请页为 404、没有邀请或提示失效时，检查当前账号与目标库是否正确，再请主人在同一协作者管理页确认受邀用户名、Pending invitation 状态及邀请是否仍有效；可由主人把官方邀请链接交给接收者本人。仅在确证需要且获得相应授权后重发，不反复登录、重发或把 404 当作邀请未发送的证明。

**完成标准。** 发出后核对待接受状态；接受后重新验证仓库访问权限。用户说“已接受”是重新检查的触发条件，不代替访问验证。随后完成接收账号的 CLI 与 Git 验证，不能以邀请页消失或浏览器可见替代全部接入成功。

### AI 执行与验证

以下操作按上面的状态分支选用；已满足完成标准的步骤直接跳过。

1. 检查 OS、架构、宿主与本机绑定、Python 3.12+、Git、GitHub CLI。已存在则复用；需要安装时，当前请求明确涵盖安装即可在新目录使用官方来源完成，遵循下文固定版本和校验要求。缺安装权限或需要系统管理员确认时只暂停该步骤，不让用户手动执行本可由 AI 完成的一串命令。
2. 使用不输出凭证的方式核实账号，例如 `gh api user --jq .login`；使用 `gh repo view OWNER/REPO --json nameWithOwner,visibility,viewerPermission` 验证目标库。禁止 `gh auth token`、读取凭证文件或索要密码/Token/私钥。仓库 404 可能是无权限或地址错误，不直接声称仓库不存在；网络失败不当作未登录。
3. 已知需要邀请或接受邀请时，先执行上面的对应分支，仅暂停依赖它的工作；不是等完成 CLI 和 Git 检查后才指导邀请。需要邀请的不同账号须先通过邀请与接受流程的完成标准，再继续清单读取。
4. 按状态表确需认证时，AI 在允许的交互终端中启动 `gh auth login --hostname github.com --git-protocol https --web`，使用用户指定的浏览器打开官方设备授权页，明确“本次授权给接收账号 RECIPIENT 的本机 GitHub CLI”。AI 完成本次设备码填写及授权范围已明确的普通页面确认；用户只处理登录凭证、验证码、双因素认证、宿主强制确认或明确保留的批准。页面要求额外范围时先说明，不顺带增加权限。若宿主要求用户输入设备码，则在本地交互界面交接，不要求复制进聊天。设备码只在本次进程内短时传递或本地交互界面使用，不保存到文件、聊天记录或共享库；剪贴板须确认为本次进程刚生成的码，不能假定旧剪贴板仍有效。无交互终端时只给这一个必要命令及操作说明。完成后重新验证 CLI 实际账号和仓库；授权未结束或已过期时先检查旧进程，不并发启动多个授权，不因网页已登录而报告 CLI 已认证。
5. 验证 Git 与 GitHub CLI 的认证链路：`gh api` 成功不等于 `git clone/pull/push` 能认证。先使用目标仓库的 `git ls-remote` 验证 Git 读取；不得将 Token 拼进 URL、命令或配置。若 Git 缺凭证衔接，在本次 Git 子进程中用 `GIT_CONFIG_COUNT`、`GIT_CONFIG_KEY_n`、`GIT_CONFIG_VALUE_n` 配置 `credential.https://github.com.helper`，值为调用已核实 GitHub CLI 绝对路径的 `!"<gh绝对路径>" auth git-credential`（按当前平台正确引用）。保留已有进程级 Git 配置项，环境仅限本次目标仓库命令；不自动执行会写全局配置的 `gh auth setup-git`。认证失败区分网络、账号、仓库权限与 helper 路径，修正后再次验证，不重复要求用户登录。
6. 可读取仓库后，先只读取得远端清单，比较本机缺少、版本不同、身份不明的 Skill/MCP/插件；用户已明确选择的条目直接继续，否则先让用户选择，不默认全量恢复。选定后分别处理：自建资源在新目录 clone 并核对分支、提交、同名资源，按 safe-sync.md 检查所有命令目标后建立源码同步绑定、预览与分发；第三方只读取安装索引，按 third-party-updates.md 核实官方来源和最新稳定版本后从原生渠道安装，不加入源码同步绑定，不从仓库旧快照分发。安装与更新均服从用户显式版本限制，生成中文目录。审查模式禁止使用会隐式应用全部配置目标的 pull。用户已要求安装此 Skill 时，授权范围内完成宿主安装；已有同名内容不得直接覆盖。首次没有 Skill 可用时，接收电脑的 AI 可读取用户提供的已审核包说明来引导安装，不能形成“必须先运行未安装 Skill”的循环。
7. 只恢复时验证读取权限即可，不用试推送证明读取。用户明确需要双向同步时检查写权限，并仅在已授权资源/分支范围提交和推送；无业务变更时不制造测试提交。有意做写入验收须在已授权测试路径中保留可核对证据。
8. 验证文件摘要、链接目标、宿主发现、实际 Skill 调用、目录内容与同步状态。需要用户重新加载宿主或发起新对话时明确提示；宿主发现/调用尚未完成则标未验证，不能以 clone 成功代替全部对接成功。成功后只将非敏感路径、权限验证结果和实际状态写入库外本机绑定/记录。

### 需要用户配合时的提示格式

一次只提出当前阻塞动作，包含“具体操作者及账号 → 浏览器与可点击页面 → 导航路径或按钮 → 为什么交给用户 → 完成标准和 AI 下一次检查”。“打开收到的邀请”“登录你自己的账号”“完成授权后告诉我”都不足以单独作为操作指引。链接来自已确认仓库和实际页面；AI 未成功打开就说“请打开”，只有看到实际页面才说“已打开”。

仅在确有必要交接时使用接受邀请模板（替换全部占位符并说明实际阻塞原因）：
> 当前 **具体工具限制/用户保留决定** 需要你操作：在 **指定浏览器名称** 确认右上角账号是 **RECIPIENT**，打开 [OWNER/REPO 的仓库邀请](https://github.com/OWNER/REPO/invitations)，确认仓库名称后点击 **Accept invitation / 接受邀请**。完成后我会重新验证仓库权限。若显示 404 或没有邀请，我会先核对账号，并请主人确认邀请状态，不让你反复登录。

等待用户操作期间可继续不依赖认证的本机检查；没有答复不能视为已授权或已完成。已授权且可以由 AI 执行的步骤不再次请求确认；只有新权限、冲突覆盖、账号不符或缺少真实信息时提出必要问题。不会自动切换账号、代替用户决定受邀人，或将一般安装授权扩展为仓库邀请。

在仓库外 `bootstrap-progress.json` 记录已确认仓库/接收账号/操作范围、观察到的浏览器与 CLI 身份、邀请阶段、API/Git 验证结果及当前待谁操作；每项注明证据来源与时间，未知就保留未知。续接时检查实际页面、CLI 与旧授权进程，复用仍有效的选择和认证，不凭旧记录宣称成功。记录不保存设备码、凭证、邀请链接中的标识或完整敏感页面。

## 1. 定位本机绑定与依赖

优先调用 `python <Skill>/scripts/sync_session.py --locate`；无指针时使用已核实路径显式 --binding，不靠旧聊天猜路径或扫描账号配置。参考 [绑定示例](../assets/local-binding.example.json)。核对已有 Python/Git/gh 实际路径与版本，PATH 找不到不代表未安装；只检查用户已给定及已有记录的位置。

运行本项目脚本需要 Python 3.12+ 和 Git。使用完整可执行文件路径验证，不改 PATH、HOME、CODEX_HOME 或全局 Git 配置。缺依赖时按本次安装授权从其官方来源取得适用平台版本，核对官方校验和并记录；不覆盖已有安装、不执行未知脚本。GitHub CLI 仅在实际需要账号/API/建库时使用，已有认证直接复用。

## 2. 取得独立管理器源码

公开安装源为 https://github.com/fofiwo/ai-toolbox-sync-skill 。固定实际提交，核对根目录 SHA256SUMS.json，按 INSTALL.md 安装完整 skills/ai-toolbox-sync 目录。公开包默认空收藏，与私人库访问权限无关。已有安装先对比来源、旧基线和本地修改，走 [自维护](self-maintenance.md)，不能拿空包覆盖真实收藏数据。

UPSTREAM.json 与随附历史许可只记录早期第三方材料，不参与命令执行、依赖安装或升级决策。

## 3. 建立本机映射，再逐项恢复

按 [原生 Git 工作流](git-workflow.md) 在新目录取得获准仓库；读取清单让用户选择，比较实际宿主内容。绑定只保存本机 Git 根、Python/Git/gh 路径、授权、journal 和所选资源映射，机器状态在库外。不初始化已有库，不自动发现全部宿主目标。

旧绑定保留原 Git 根、身份、journal、决策和收藏；遗留 CLI/XDG 字段不再执行，也不删改以便回退。逐文件应用前核对差异、基线和在用进程；依赖、MCP/插件注册在本机单独配置。文件、宿主发现与实际调用分别验证，其他平台未实测不能外推。

## 每机任务入口启用

按 [任务触发同步](task-sync.md) 核实 taskSync 策略及授权证据。已有用户授权明确涵盖这台电脑和同一资源范围时可继承并记录；否则一次说明仅修改前实时比较、有差异先给摘要与建议让用户选择、修改结束只提醒、用户主动同步才上传、安装后询问纳管、新建等用户主动收集，并请求开启。安装本 Skill 不等于全局规则已生效，规则模板只按用户授权写入对应宿主；新会话实际加载仍须验证。不迁移开发机路径、凭证或运行日志，不默认后台服务。


## Agent 文档

整份全局文档使用 `kind=agent-document`，按 [Agent 文档流程](agent-documents.md) 发布、导入及同步。复制导入提示只表达意图，执行时仍须确认目标与覆盖/整理/追加/插入方式。新派生文档登记独立身份，来源固定到提交；本机整份绑定不能随 Git 分享。目录新增 Agent 文档分类，支持复制导入或同步指令；同步指令必须匹配本机自己的绑定，无绑定时停止。五轴状态沿用，不将本地快照写成功或目录复制成功当成 GitHub 同步成功。
